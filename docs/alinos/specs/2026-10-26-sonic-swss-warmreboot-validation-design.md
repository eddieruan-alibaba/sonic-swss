### 被测恢复链路

1. `fpmsyncd` 接受 FPM 连接后调用路由 helper 的 `checkAndStart()`；仅在 warm start 且 `DEVICE_METADATA/localhost/nhg_fib=enabled` 时初始化 NHG Assist 并加载状态（`fpmsyncd/fpmsyncd.cpp:181-237`）。
2. Assist 继承 `AppRestartAssist` 复用构造/注册，但用自己的 FSM 判断 `inProgress()`；其逻辑状态为 `NONE → INITIALIZED → RESTORED → RECONCILING → RECONCILED`（`fpmsyncd/nhgWarmRestartAssist.cpp:159-178`）。不能把子类状态与基类缓存/定时器状态视为一套机制，也不要求每个瞬态都在 STATE_DB 可见。
3. 恢复期通过 `FpmLink::processFpmMessage()` 截获消息。5000/5001 存入 NHG 队列；普通 NEW/DELROUTE 和 3000/3001 存入路由队列；6000 存入 resolve 队列。localSID 1000/1001、PIC context 2000/2001 不在此拦截集合，仍走既有路径（`fpmsyncd/fpmlink.cpp:280`、`fpmsyncd/nhgWarmRestartAssist.cpp:410-447`）。
4. 空 `ROUTE_TABLE` 会使路由 helper 立即完成并返回 false；daemon 用 `runRestoration() || assist.inProgress()` 启动主定时器。EOIU 检查仍只看路由 helper，因此空表场景当前依靠主定时器结束，不承诺走 EOIU 快路径（`warmrestart/warmRestartHelper.cpp:102-133`、`fpmsyncd/fpmsyncd.cpp:223-235,299-330`）。
5. `RouteSync::onWarmStartEnd()` 按 NHG 恢复 → 路由回放 → resolve 回放 → suppression 处理 → 路由 helper reconcile 执行（`fpmsyncd/routesync.cpp:3983-4008`）。NHG 内先处理普通单跳，再拓扑处理有 Sonic 对象的 NHG；以排序后的完整字段值向量（FV）匹配旧 APP_DB 项并尝试复用 ID，清理未匹配旧项。
6. NHG 阶段在路由和 resolve 回放前就设置 `fpmsyncd-nhg` 的 `RECONCILED`（`fpmsyncd/nhgWarmRestartAssist.cpp:668-677`）。所以该状态只能证明阶段到达，完整验收还需回放完成、引用一致和数据面证据。
7. 正常 select 循环的信号退出分支仅当启动时的 `warmStartEnabled` 和 `nhg_fib` 均开启才保存状态；断连异常中的信号退出只 flush，未调用保存（`fpmsyncd/fpmsyncd.cpp:258-272,351-362`）。首次 warmreboot 和不同信号时点必须分别测量，不能由注释推定保存可靠。

| 对象 | 实际用途 | 验收关注点 |

字段与加载逻辑依据 `fpmsyncd/nhgWarmRestartAssist.cpp:191-407`，正常回读写入依据 `fpmsyncd/routesync.cpp:3125-3173`，应用名依据 `fpmsyncd/routesync.cpp:188`。加载器不解析保存的 `json`，实际重建输入是 FPM NHG 消息；损坏保存 JSON 与损坏 FPM JSON 是两个测试，不能期待前者触发后者的解析错误。停机保存不先清空整张状态表，恢复也不统一刷新正常回读字段，因此该表不是完整恢复快照。

## Goals / Non-Goals

**目标**

- 建立从编译到物理转发的逐级证据链，区分已有覆盖、拟新增用例和实际运行结果。
- 验证无变化对象保持、恢复期变化的最终一致性、ID 安全和有限时间内结束；两个迁移适配必须有回归用例。
- 将测试失败准确分类为环境阻塞、编译问题、组件/集成缺陷或物理数据面问题，不混淆责任边界。
- 给下一阶段实现和设备执行提供明确的输入、断言、关卡与安全边界。

**非目标**

- 本轮不实现测试、不修复下列风险、不升级设备、不触发重启、不重构 Assist，也不修改 CI、数据库结构、权限或 TLS 配置。
- 不声称支持跨版本升级恢复、掉电恢复、SIGKILL 下的优雅保存或通用全系统 warmreboot 验收。
- 不替代整个 SONiC warmreboot 测试体系；物理验收限定为所选平台、路由栈版本和业务拓扑。
- 不为未知设备虚构规模、丢包预算或收敛时间承诺；预算缺失时禁止给出性能达标结论。

## Decisions

### 1. 分四层验证，按关卡推进

| 层级 | 执行环境与用途 | 必备证据 | 不承担的结论 |
|---|---|---|---|
| L1 编译/组件 | 可信 Linux/Bookworm；编译真实 fpmsyncd，运行 GTest 和 mock 全量回归。优先扩展现有测试文件。 | 编译日志、命令退出码、测试清单、GTest XML、失败堆栈；按需在隔离环境运行 ASAN。 | 真实定时器/信号执行、Redis 持久化及硬件流量。 |
| L2 真实进程集成 | 专用可丢弃 DVS，真实 fpmsyncd、helper、Redis；由确定性 TCP FPM 测试端替代 Zebra。 | FPM 输入序列、接收侧阶段观察、真实定时器/EOIU、进程状态、Redis 快照和对象写操作证据。 | 真实 Zebra 生产协议正确性、系统重启编排、物理 ASIC 保持和丢包预算。 |
| L3 设备状态 | 授权隔离设备，使用实际 BGP/Zebra、swss、syncd 和 warmreboot 流程。 | 版本/配置、重启原因、服务状态、路由/数据库/硬件快照、重启后增删改结果。 | 未测流量的无损结论。 |
| L4 物理数据面 | 外部流量仪在设备重启期间持续测量，分别覆盖保持业务与受控收敛业务。 | 每流序列/计数、时间轴、中断/丢包/重复/乱序结果及稳定后转发。 | 超出所测拓扑、速率、平台和次数的承诺。 |

选择理由：仅单测会漏生命周期；直接真机难定位且代价高；全套 Zebra 的 L2 更接近系统但难以确定性构造私有消息时序。因此选分层加确定性 L2，真实生产者与系统编排在 L3 验证，不建设通用测试平台。若所选 DVS 缺依赖，L2 阻塞，不静默换成 mock 或随意另建第二套执行框架。

关卡约束按层级和场景生效：没有设备或流量预算不阻塞 L1/L2 开发；已确认的组件正确性失败阻止相关设备验收，但允许带明确诊断目的的隔离复现。不得把“所有层先通过才能继续测试”形成的循环依赖当作流程。

#### 1.1 L2 的生产者与协议边界

- 测试端在与 fpmsyncd 相同的网络命名空间连接 `127.0.0.1:2620`；不新增生产监听接口。采用 FPM v1/type 1、四字节头、网络字节序总长度、四字节对齐、总长不超过 16384 的合法帧，承载完整 Linux netlink 消息；正向用例覆盖 TCP 分片和合帧。依据 `fpmsyncd/fpmlink.cpp:134-263`、`fpmsyncd/fpm/fpm.h:69-143`。
- 在专用夹具中通过 Supervisor 停止并确认 Zebra 不会争抢连接，同时独占 EOIU 写入；不能直接复用 `tests/conftest.py:784-786` 的 kill+sleep 当作隔离屏障。退出时恢复本夹具改变的服务状态；仅清理本夹具创建的容器/命名空间，不清空共享 Redis。
- NHGFIB 使用库兼容 JSON、匹配的 NHA_ID 与真实命名空间 ifindex；6000 使用其 rtmsg/JSON 格式。测试端持续排空返回数据，避免背压；返回 route offload 消息不是通用消费确认。每次重连重放完整期望转发状态，而非仅发送新增量。
- 现有基础只有 DVS 生命周期和 DB 接口。TCP 测试端、私有消息序列化、独占夹具和观察控制器均属后续新增测试能力，不宣称已有。首次恢复的冷预热在真实 daemon 上完成，不用直接灌 APP_DB 替代端到端种子；直接造损坏 DB 只用于明确的 L05 负向场景。

#### 1.2 恢复轮次、输入截止点与观测方式

一轮标识为 `(run_id, process_incarnation, accept_ordinal)`：进程号可复用，另记启动时刻；以服务端接受连接的事件递增 ordinal。每次 accept 都会重新进入恢复/定时器初始化，而 `RouteSync` 在同进程重连间存活，故不把 reconnect 视作全新内存状态。

截止点不是 `send()` 返回，而是预先列出的最后一条消息在接收端完成 buffer append/实时 handler 的观察点，且必须先于 `onWarmStartEnd()` 入口。对非空表 EOIU 场景，观察齐全后再写双栈 EOIU；保持 TCP 连接，不能靠关闭连接制造屏障。超时场景记录真实触发与入口，截止后的消息单列为实时更新，不拿错误归类的数据证明缓冲覆盖。

选用**隔离 L2 的外置 GDB/MI 返回断点观察**，利用符号关联类型、净载荷摘要和所属轮次；缓冲调用还须核对 FSM、队列长度增量及新增项摘要，排除提前返回被误记为入队，实时路径须核对目标 handler 的完成。不添加生产 ACK、控制端口或测试钩子；控制器本身先用短序列验证观察计数。缺调试符号或合法调试能力时，时序断言记 BLOCKED，不自动变更权限。相比仅 sleep/发送日志，此方式可证明因果；相比先引入内核探针框架，适合小规模定向测试。

断点会扰动调度，因此观察运行只证明生命周期和因果关系，不能用于性能达标。用同提交、无调试器的真实 daemon 另做有限时间完成与状态/流量测量；该运行若没有接收证据，不声称逐条消息进入了某一缓冲窗口。观察耗时导致输入未赶上已设截止点时，该时序子例为实验前提不满足，不将其计作业务失败或静默重试至通过；任何已观察到的错误仍保留 FAIL。

### 2. 以独立期望状态为判定依据

最小普通拓扑含两个可区分下一跳、一个 ECMP NHG和两条引用路由；它只验证路由共享一个 RIB NHG，不等于管理器的共享 Sonic 对象路径。共享/PIC 拓扑另用两个符合 received SRv6 条件的不同 RIB NHG，下一跳公共部分相同而 VPN SID 不同，再加入依赖它们的组合 PIC。最小集用于定位，规模集使用冻结的业务规模。

- 保存恢复前状态 `S0` 和有轮次/顺序的输入账本 `E`。小用例优先显式声明独立语义预期，NEW 按对象键替换，DEL 移除，resolve 撤销/恢复更新对应主备依赖；缺依赖和环属于单列负向输入。真实生产者场景由配置/业务账本给出语义预期，无重启参考实例仅作交叉核对，不独自证明正确。
- 预期值生成不得调用 Assist 或同一活管理器的 `RIBNHGEntry::setEntry()`。后者会检查/增加共享引用，临时对象析构不撤销该动作（`fpmsyncd/nhgmgr.cpp:822-824,938,1261-1276`）；用它作“只读 oracle”既会复制缺陷又会扰动被测状态。
- 将**语义正确性**与**标识保持**分开断言。字段顺序可忽略；`nexthop`、`ifname`、权重按关联元组比较，不能分别排序；SID 序列、主备角色和重复成员数量有意义，不能丢弃。
- 固定合法表示且完整 FV 匹配的无变化对象必须保留可匹配的旧 Sonic ID，多个等价候选按候选集合而非唯一 RIB 映射核对。RIB 改号/成员序列重排另设表示变化子例：语义仍须正确，记录未匹配、新 ID 和 churn；当前精确 FV 算法不提供任意等价表示的 ID 保持保证，不能由该子例推导无损。该限制不得放宽固定表示子例的保持断言。
- PIC 以 VPN SID、成员/主备语义和引用单独关联。相同 NHG FV 不证明相同 PIC；保存结构按 Sonic NHG ID 索引会合并关联，复用方法只设置 PIC ID而不重建 PIC 内存表（`fpmsyncd/nhgWarmRestartAssist.cpp:335-349`、`fpmsyncd/nhgmgr.cpp:2010-2017`）。必须检查 PIC 查找、恢复后组合创建、删除一个共享者以及删除最后共享者后的对象/ID释放。
- NHG/PIC 各自的活 ID 必须非零且不碰撞；分配器计数可以低于已用区间，只要占用保护正确。仅在 APP_DB 出现而缺保存记录的 ID 也要覆盖，删除后检查占用释放而不要求全局计数回退。资源引用泄漏不能靠最终表项仍在而判通过。
- 写操作按表、键、阶段和目的分类：固定表示静态对象禁止不必要的删除/重建；状态上报、合法新建/撤销、resolve 收敛写入不计为违规。不能要求所有数据库全程零写入。ASIC OID 映射为语义图，硬件保持另需事件证据；缺事件可观测性时“无 churn”子断言为 BLOCKED，不用两张相等快照代替。
- 三类队列不保持跨类型全局顺序。测试预期按生产者事件语义而非当前分队列回放顺序构造；截止点前输入与后续实时输入分别核对，最后均须满足引用和转发语义。

### 3. 最小验证矩阵

下表均是**拟执行的验收要求**，不是新增测试已经存在或已经通过。L1/L2 可先用确定性输入复现；动态物理场景在静态关卡通过后实施。

| 编号 | 层级 | 场景与输入 | 核心断言 |
|---|---|---|---|

### 5. 设备契约、时间轴和证据

每一层执行前冻结其运行清单：L1 必须有提交、镜像、依赖、架构、编译配置、测试清单与日志目录；L2 另需独占 DVS、协议/符号能力、输入子例、恢复/EOIU/停机期限、观测模式和有限完成期限；L3/L4 再加入设备/ASIC命名空间、实际生产者与 finalizer 版本/成员、业务拓扑规模、授权窗口和恢复方案；L4 还必须有流量模型、预算和测量精度。缺少某层输入只阻塞该层，不阻塞独立的较低层工作。

所有期限和预算注明单位、观察起止点及来源；数值在运行前确定而不是根据结果反推。测试用的有限等待期限不是产品 SLA。资源检查分两类：对象/引用/allocator占用应按确定性生命周期释放；RSS、CPU和处理耗时按冻结规模及预算记录，三轮只能作为重复性样本，不证明长期无泄漏。60 秒稳定窗口和三轮是最低探索样本建议，可在运行前增加，不得在结果失败后缩短或挑选轮次。

采集时间轴：

1. **重启前稳定阶段**：建立 BGP 邻居和业务，保存配置及逻辑状态；推荐至少 60 秒稳定观测，记录逐流背景丢包和资源指标。若背景已经不稳定，暂停验收。
2. **发起与停机阶段**：记录授权动作、信号接收、保存/flush 完成、退出时刻及 database 服务可用性。保存必须在实际服务停机期限内完成，“默认 10 秒足够”不是本次结论。
3. **重放与恢复阶段**：记录 FPM 连接、状态加载、消息输入、EOIU/timeout、NHG 阶段完成、route/resolve 回放完成及路由 reconcile。使用同一时间基准或记录时钟偏差。
4. **恢复后稳定阶段**：比对状态与硬件语义，推荐再观测至少 60 秒；验证正常增删改和下一次恢复。预后观测时长是初始建议，不是业务性能预算。

证据包按运行编号关联：环境清单、输入事件账本、原始日志、退出码/JUnit XML、恢复前后与关键中间点的 DB/路由/硬件快照、规范化差异、每流结果和失败定位。状态快照按场景范围采集，避免全库轮询影响恢复性能；删除/重建计数优先通过测试替身或现有日志获取，重型调试采集与性能正式测量分开运行。

数据库名/表名来自实际设备 schema；ASIC/厂商查询使用平台已支持的只读接口。不在生产设备注入畸形消息，不自动覆盖管理配置、触发共享设备重启或上传含敏感配置的原始证据。

### 6. 判定标准

| 关卡 | 通过条件 | 不通过或阻塞的条件 |
|---|---|---|
| G0 可复现环境 | 对当前层级的提交、镜像、依赖、能力、配置和日志可追踪；设备层另有授权。 | 只阻塞缺少相应前置条件的层/子例，不把设备预算作为 L1 门槛。 |
| G1 编译和组件 | 真实 fpmsyncd 编译成功；现有 15 用例、矩阵对应新增用例和全量回归均实际执行，零失败，异常输入无内存错误。 | 任何失败；过滤为空；skip/xfail 被算作 PASS；只运行旧测试却宣称矩阵全覆盖。 |
| G2 集成恢复 | 适用 C/L 子例按各自健康/负向目的完成；健康场景的NHG、route、resolve和下游可见状态正确，后续更新正常。 | 有效证据显示错表/错引用、无限缓存、状态破坏、跨轮残留或超过已设期限为 FAIL；没有时序观察能力为对应断言 BLOCKED。 |
| G3 设备状态 | 适用 S 场景满足独立语义、限定的 ID 保持及硬件检查；健康首轮和后续轮都真实热恢复。 | 意外 cold fallback、崩溃、状态不一致；只核对计数/finalizer退出；缺能力但宣称全范围通过。 |
| G4 数据面 | 冻结条件下每流、每轮指标满足预算；无持续黑洞/错误出口。 | 有效测量超预算为 FAIL；预算/能力不足或误差无法区分达标与否为 BLOCKED；仅 DB/DVS证据不予判定。 |

时间分开记录：`T_logic` 为加载开始至 NHG/route/resolve及路由核对调用结束；`T_restore` 为加载开始至必要 flush 后期望状态实际可见；`T_system` 从发起系统 warmreboot 至运行前定义的系统就绪点。报告生成或遍历快照耗时不计作业务处理。主定时器值只决定触发等待，不是全部耗时上限；预先冻结的完成期限包含等待、处理、下游可见及测量容差。空表使用主超时路径；FPM 未连接用独立系统期限约束。

轮询/日志时间有误差时保留区间：上次未就绪与首次就绪形成恢复时间上下界，另记录时钟和采集精度。只有区间上界不超过预算才 PASS，下界已超过预算则 FAIL；区间跨越预算为 BLOCKED（测量精度不足）。阶段顺序以调用/日志事件为证，不能把日志到达采集器的顺序当作函数执行时序；断点观察数据不参与性能判定。

流量按每条流记录发送/接收序列、重复、乱序、损失和最大连续中断。停止计量后保留预先规定的接收排空窗口，避免把在途报文算丢；不能用简单 TX−RX 抵消重复。恒定且校准的速率才允许用连续丢包数/速率估算中断；否则需要带足够精度的时间戳。静态保持和受控撤销流事先分组，后者按预期收敛行为判定，不在结果出来后排除坏流。若声称“无损”，冻结零丢包预算和对应测量能力；未知预算可用于探索性测量，不能签署性能通过。

每个子例预先声明 `purpose`（健康恢复、拒绝/降级安全、诊断或性能）、`expected_outcome`、适用层和断言列表。健康首轮不允许人工补 restore_count 冒充成功；故意缺计数负例可以对固定依赖版本的 cold fallback 安全行为给 PASS，但只能证明该负例，不能计入 warm 成功次数。损坏保存 JSON 未被消费时，预期是不影响所需元数据/FPM重建，不要求出现 JSON 错误日志。

结果仍为 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN`、`NOT_APPLICABLE`。预期拒绝本身不是测试失败；偏离预期或破坏有效状态才是 FAIL。实际观察到的产品错误即使同时缺其他证据仍保留 FAIL，不改记环境阻塞。汇总优先级为 FAIL、BLOCKED、NOT_RUN、PASS；有正式范围依据的 NOT_APPLICABLE 从该范围排除并列明。只有全部必测子例通过才可声明相应范围验收通过。重试保留原结果和新运行编号；任何已知缺口都不因登记在风险表而自动豁免。
